# Техническое задание: UI Панели Archicad

## «Редактор описаний свойств»

### Статус документа

ТЗ актуализировано с учётом уже реализованного `dialogs/index.html`.

**Важно:** существующую работающую UI-архитектуру не переделывать без необходимости. Следующий этап — завершить интеграцию с C++ Add-On и устранить расхождения между mock-логикой и реальными данными Archicad.

---

# 1. Архитектура и стек

- Среда выполнения: встроенный браузер боковой панели Archicad (Windows).
- Весь интерфейс поставляется одним файлом:

`dialogs/index.html`

- Только Vanilla HTML + Vanilla JS.
- Запрещены React, Vue и другие JS-фреймворки.
- Запрещены внешние CSS-файлы.
- Запрещён `<style>`.
- Стили задаются только через inline `style="..."`.
- Для общей темы допускается использование CSS custom properties, заданных непосредственно на корневом `<html>` через inline-style и изменяемых из JS.

Текущая реализация уже соответствует этим ограничениям.

---

# 2. Адаптивность

- Интерфейс должен корректно работать при Windows DPI:
  - 100%;
  - 125%;
  - 150%;
  - 175%;
  - 200% и выше.

- Минимальная ширина панели — около 150 px (интерфейс и панель сужены на 40% относительно прежних 250 px; ширина окна палитры по умолчанию — 230 px, `Tools/AddOn.grc.in`).
- Минимальная ширина ограничивается также на стороне C++.
- Не допускаются:
  - наложение элементов;
  - обрезание текста;
  - горизонтальная прокрутка при поддерживаемых размерах;
  - разрушение layout при изменении ширины панели.

- Размеры должны использовать логические единицы (`rem`, `%`, `flex` и т. п.), а не неоправданно жёсткие физические пиксели.

---

# 3. Дизайн и темизация

Стиль:

- современный;
- минималистичный;
- визуально близкий к интерфейсам Archicad;
- без избыточных декоративных элементов.

Поддерживаются:

- светлая тема;
- тёмная тема.

При переключении темы должны корректно изменяться:

- фон;
- текст;
- вторичный текст;
- границы;
- поля ввода;
- выпадающие списки;
- hover-состояния;
- активные элементы;
- кнопки;
- блоки предпросмотра;
- редактор DSL;
- список свойств.

Не должно оставаться элементов, визуально принадлежащих предыдущей теме.

# 4. Глобальная структура

Интерфейс состоит из двух зон.

## 4.1. Левая панель навигации

Фиксированная логическая ширина.

Вкладки сверху вниз:

1. Монитор
2. Синхронизация
3. Нумерация
4. Суммирование
5. Спецификация

Требования:

- вкладки переключают рабочую область;
- активная вкладка визуально выделена;
- подписи повёрнуты на 90° внутрь панели;
- текст читается снизу вверх;
- в нижней части панели находится переключатель темы.

Текущая реализация вертикальных подписей и переключения вкладок уже существует.

## 4.2. Рабочая область

- занимает всё оставшееся пространство;
- не имеет горизонтального overflow;
- содержимое зависит от активной вкладки;
- каждая вкладка должна самостоятельно управлять вертикальным overflow.

# 5. Вкладка «Монитор»

Назначение: просмотр текущего выделения, классификации и свойств элементов.

## 5.1. Информация о выделении

В верхней части:

**Выделено элементов: N**

Дополнительно:

- кнопка `↻`;
- обновление количества выделенных элементов;
- обновление должно обращаться к текущему состоянию Archicad, а не к сохранённому значению.

---

# 5.2. Классификация

Отображается классификация текущего выделения.

Если классификация едина:

- показать общий путь классификации.

Если классификации различаются:

- явно показать `РАЗНАЯ`;
- показать варианты классификаций;
- предоставить выбор единой классификации;
- предоставить действие **«Применить ко всем»**.

После применения классификации интерфейс должен обновить состояние данных.

В текущем HTML этот блок и контракт `getClassification()` уже предусмотрены, но реальный C++ вызов пока заменён mock-реализацией.

---

# 5.3. Фильтр свойств

Предусмотреть:

- поле ручного ввода;
- фильтрацию списка по мере ввода;
- обычный текстовый поиск;
- regexp в формате `/шаблон/`;
- список преднастроенных фильтров.

Минимальный набор:

- Все свойства;
- Только IFC;
- Только геометрия;
- Незаполненные.

Фильтрация должна выполняться без повторного обращения к C++, если все необходимые данные уже загружены.

---

# 5.4. Список свойств

Свойства:

- группируются по системным группам Archicad;
- отображаются вертикальным списком;
- группы можно сворачивать/разворачивать;
- состояние групп сохраняется во время работы панели;
- список имеет вертикальную прокрутку.

Текущая реализация уже поддерживает группировку и сворачивание групп.

---

# 5.5. Строка свойства

Каждая строка должна содержать:

1. название свойства;
2. количество элементов, у которых свойство существует;
3. **непосредственно под названием — значение/значения свойства мелким шрифтом**;
4. кнопку сброса справа.

Пример:

```text
Толщина стены (5/5)
250 мм ×5                                      [↗]
```

Если значения различаются:

```text
Толщина стены (5/5)
250 мм ×2
300 мм ×2
— не задано — ×1                              [↗]
```

Для свойства, которого нет у части элементов:

```text
Марка (3/5)
A-101 ×2
A-102 ×1
```

---

# 5.6. Цветовое кодирование

Сохранить существующую логику:

- акцентный/синий цвет — свойство присутствует у всех выделенных элементов;
- обычный цвет — свойство есть только у части элементов;
- рядом с названием отображается количество:

`(3/5)`

где:

- `3` — количество элементов, у которых свойство существует;
- `5` — общее количество выделенных элементов.

---

# 5.7. Отображение значений

Это ключевое изменение интерфейса.

**Значения всех отображаемых свойств должны быть видны одновременно.**

Пользователь не должен:

- выбирать свойство;
- нажимать отдельную кнопку;
- открывать отдельную панель;
- ждать отдельного запроса для просмотра значения.

Значение отображается непосредственно под названием свойства.

### Если значение одинаковое

Показывается одно значение:

```text
Высота
3000 мм
```

### Если значения различаются

Показываются все уникальные значения:

```text
Высота
3000 мм ×3
3200 мм ×1
— не задано — ×1
```

### Если значение отсутствует

Использовать:

`— не задано —`

### Если значения длинные

Разрешается:

- перенос строки;
- ограничение количества строк;
- визуальное сокращение с tooltip при наведении.

Но значение не должно исчезать полностью.

### Размер

Значение должно быть:

- заметно меньше названия;
- вторичным по визуальному приоритету;
- достаточно контрастным для чтения в обеих темах.

# 5.8. Удаление старого блока значения

**Отдельный нижний блок «Значение свойства» полностью удалить.**

Удалить:

- сам контейнер;
- текст «Выберите свойство в списке выше, чтобы увидеть значение»;
- отдельный `renderValueBlock()`;
- логику загрузки значения только после выбора свойства;
- зависимость отображения значения от `monitorSelectedPropertyId`.

В текущем HTML этот блок существует отдельно и именно его необходимо убрать.

Выделение строки свойства можно оставить для:

- визуального состояния;
- будущего редактирования;
- дальнейших действий.

Но **выбор строки не должен быть необходим для просмотра значения**.

# 5.9. Данные свойств

C++ должен вернуть данные сразу в форме, пригодной для построения всего списка.

Рекомендуемый логический контракт:

```text
{
    elements: [
        {
            guid,
            properties: [
                {
                    propertyGuid,
                    name,
                    group,
                    value,
                    valueType
                }
            ]
        }
    ],
    count
}
```

На стороне JS данные должны агрегироваться в:

```text
{
    id,
    name,
    group,
    allHave,
    countWithProperty,
    values: [
        {
            value,
            count
        }
    ]
}
```

Где:

- `allHave` — свойство присутствует у всех элементов;
- `countWithProperty` — количество элементов со свойством;
- `values` — уникальные значения;
- `count` — количество элементов с конкретным значением.

**Важно:** C++ не обязан заранее агрегировать значения, если это усложняет native API. Допустимо вернуть значения по каждому элементу, а агрегацию выполнить в JS.

Но C++ обязан передать **реальное значение свойства**, а не только `propertyGuid` и имя.

Сейчас `getPropertiesList()` получает значения из C++, но при преобразовании ответа UI фактически их выбрасывает.

---

# 5.10. Производительность

Нельзя делать отдельный native-запрос для каждого свойства.

Неправильно:

```text
получить список свойств
→ получить свойство 1
→ получить свойство 2
→ получить свойство 3
→ ...
```

Правильно:

```text
получить выделение
→ одним запросом получить необходимые свойства и их значения
→ построить весь UI в JS
→ фильтровать/группировать локально
```

Это особенно важно при большом количестве свойств.

---

# 5.11. Сброс свойства

Справа от каждой строки:

**кнопка сброса к значению по умолчанию.**

Существующая визуальная концепция цепочки сохраняется:

- нормальное состояние — замкнутая цепочка;
- операция — активное/разомкнутое состояние.

При нажатии:

1. заблокировать повторный клик;
2. вызвать C++;
3. дождаться результата;
4. при успехе повторно получить актуальные данные свойства/выделения;
5. обновить отображаемое значение;
6. вернуть кнопку в нормальное состояние.

Существующий mock-контракт `resetPropertyToDefault(propertyId)` уже предусмотрен.

- команды;

# 10. JS ↔ C++ Bridge

Все обращения UI к Archicad должны идти через единый `ACBridge`.

Нельзя разбрасывать вызовы native API по UI-коду.

Каждая операция должна иметь:

- JS-функцию;
- чёткий входной контракт;
- чёткий JSON-ответ;
- обработку ошибки;
- состояние загрузки.

Текущий файл уже построен именно вокруг такого подхода. `ACBridge` является mock-слоем, который впоследствии должен быть заменён реальным JS-мостом, сохранив контракты функций.

---

# 11. Ошибки и состояние UI

Каждый native-запрос должен иметь три состояния:

1. загрузка;
2. успешный результат;
3. ошибка.

Ошибки C++ не должны приводить к:

- зависанию интерфейса;
- бесконечному «Загрузка…»;
- разрушению списка;
- закрытию панели.

Ошибка должна отображаться пользователю компактно и понятно.

---

UI должен получить актуальные данные.

Нельзя оставлять старые значения на экране после успешного изменения Archicad.

# 15. Критерии готовности UI

Работа считается выполненной, если:

- при выборе 5 элементов список свойств отображает их значения сразу;
- пользователь не должен кликать по свойству для просмотра значения;
- у каждого свойства значение находится непосредственно под названием;
- при разных значениях отображаются все уникальные варианты;
- возле каждого варианта есть количество;
- отсутствующие значения отображаются как `— не задано —`;
- нижней панели значения больше нет;
- фильтр не скрывает значения;
- сворачивание групп работает;
- светлая/тёмная тема корректна;
- при сбросе свойства значение на экране обновляется;
- UI не создаёт N native-запросов для N свойств.

---

# 16. Критерии готовности интеграции с Add-On

- Все mock-вызовы, относящиеся к Archicad, заменены реальным мостом.
- JS получает реальные данные текущего выделения.
- Классификация читается из Archicad.
- Классификация может быть изменена.
- Список свойств читается из Archicad.
- Значения свойств читаются из Archicad.
- Сброс свойства реально изменяет Archicad.
- После изменения данные UI обновляются.
- Ошибки native-операций корректно возвращаются в JS.
- Формат JSON стабилен и документирован.
- UI не зависит от конкретного количества выделенных элементов.
- При отсутствии выделения интерфейс корректно показывает пустое состояние.
