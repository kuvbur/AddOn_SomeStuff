## SpecPlanning (вклад источника)

> Хеш состояния: `2101967` (2026-10-02), строки — определения в
> `SpecPlanning.cpp` (1-based, собраны clangd и сверены с исходником).

Новый внутренний модуль блока R6. Отвечает за одну сущность: **вклад одного
источника** в итоговую строку спецификации.

| Что | Где |
|---|---|
| `MissingField` | `SpecPlanning.hpp` — непрочитанное поле + признак «ошибка элемента» |
| `ContributionStatus` | `SpecPlanning.hpp` — `Excluded` / `Empty` / `Partial` / `Complete` |
| `RuleContribution` | `SpecPlanning.hpp` — источник, статус, значения по слотам, ключи, пропуски |

### Разделение двух сущностей

`Spec::Element` — ИТОГОВАЯ строка, накопительный агрегат по ключу; то, что
уходит в сверку и создание. `RuleContribution` — данные ОДНОГО источника за один
проход цикла. До R6.2 оба понятия жили в одном типе.

### Почему две фазы, а не одна

В исходном цикле `elements.ContainsKey (key)` стоит **после** чтения сумм, а
ключ известен только с конца чтения уникальных параметров. Выходные слоты
читаются только в ветке «ключа ещё нет» — то есть только для первого
представителя. Слияние фаз заставило бы читать выход у каждого источника и,
что важнее, заносило бы неполный выход второго источника в отчёт как ошибку,
хотя раньше он молча игнорировался.

### Границы

- Вклад **не накапливает вклады всех элементов модели** в отдельном массиве —
  это прямо запрещено критерием выхода R6 («нет удвоения рабочего набора»).
  Массив вкладов допускается только в regression-режиме R6.5.
- Не меняет ключи строк, порядок первого представителя и арифметику суммирования
  (это R6.3/R6.4).
- Политика отказов (`stop_on_error`, счётчики `not_found_*`, `msg_rep`) осталась
  в `PlanRuleRows`. Вклад сообщает, **что** не прочитано; решение принимает
  вызывающая.

### Раскладка в агрегат (R6.3)

| Что | Где |
|---|---|
| `RowAddition` | `SpecPlanning.hpp` — `Created` / `Merged` / `SchemaMismatch` |
| `SumContributionIntoRow` | `SpecPlanning.cpp` — суммирование в существующую строку |
| `AddContributionToRow` | `SpecPlanning.cpp` — создание или слияние в словаре строк |

**Суммирование неполных массивов — поведение, а не баг.** Сохранено дословно:

- складываются только первые `nsumm = MIN(длин)` слотов; слоты сверх `nsumm` не
  трогаются;
- слот складывается только при `isValid` у обеих сторон, иначе остаётся как есть;
- размеры никогда не выравниваются.

Строгая проверка «длины равны, иначе ошибка» была бы **улучшением, меняющим
результат**, — этого шаг не делает. Наблюдение зафиксировано в `IDEA.md` как
кандидат в **F1** (безопасность неполного расчёта), само F1 не выполнялось и
требует отдельного согласования политики.

**Порядок операций, который обязан сохраняться:**

1. при `Created` запись `outParam[keyOut] = key` делается **до** проверки схемы —
   ключ попадает в словарь даже для отброшенной строки;
2. при `Merged` источник дописывается **до** суммирования;
3. выходные слоты берутся из вклада как есть, без пересчёта и фильтрации.


### Общая выходная схема (R6.4)

`OutputSlot {rawname, value, isSum}` и `Element::out_slots` — имя и значение
слота лежат рядом, поэтому рассинхрон между `out_paramrawname[k]` и
`out_param[k]` невозможен по построению.

| Что | Где |
|---|---|
| `OutputSlot`, `OutputSlots` | `Spec.hpp` — слот и массив слотов |
| `Element::out_slots` | `Spec.hpp` — схема строки |
| `OutParam(i)` / `OutSlotName(i)` / `OutSlotCount()` | `Spec.hpp` — прежнее поведение по индексу |
| `TryGetOutSlot(i, ...)` | `Spec.hpp` — имя+значение слота, `false` вне диапазона |
| `BuildOutputSlots` | `SpecPlanning.cpp` — внутренняя, строит схему один раз на строку |
| обновление значений сумм | `SpecPlanning.cpp`, в том же цикле суммирования |

**Производительность:** схема копируется один раз на строку (как раньше два
массива имён), lookup на ячейку не добавлен — вместо обращения к имени по
индексу прямой проход по слотам. Обновление сумм не добавляет проходов.

**Двойная правда — осознанно и временно:** прежние поля `out_param`,
`out_sum_param`, `out_paramrawname`, `out_sum_paramrawname` оставлены, потому что
accessor-ы читают их. Расхождение возможно только в отладочной сборке и должно
быть поводом для теста, а не для молчаливого поведения.

Проверено `TestSpecRowSlots` — 28 проверок: порядок/имена/значения против
прежних массивов по каждому индексу, безопасный ответ вне диапазона, актуальность
сумм после слияния, неизменность выходного слота первого представителя, отсутствие
схемы у отброшенной строки, стабильность размера при трёх слияниях.


### Равносильность движков (R6.5)

Эталон «old» — **независимая реализация прежней арифметики** в
`tests/TestSpec.cpp` (`namespace legacy`): `SumInto` (прежняя арифметика
сложения) и `PlanRow` (прежняя раскладка по словарю). Ни одного вызова нового
модуля; вызовов из `Sources/AddOn/spec/` нет, в production-сборку `tests/` не
попадает. План требует именно этого: «production выполняет один движок».

Эталон **сам дочитывает выходные слоты** первому представителю ключа — иначе
сравнивались бы два разных входа, а не два разных движка.

Проверено `TestSpecEngineEquivalence` — 49 проверок: один ключ / три источника;
два ключа с перемешанными источниками; неполные массивы в обе стороны;
`isValid` с обеих сторон. Сравниваются число строк, размер `outParam`, размеры
слотов, значения сумм, порядок источников поэлементно и выходные значения.

**Урок при отладке расхождения.** Расхождение было симметричным с обеих сторон,
то есть движки равны, а ломалась сборка входа (фаза 2 вызывалась дважды).
Диагностика с размерами вклада до/после фазы 2 показала это за один прогон.
При расхождении «A против B» сначала проверять вход, а не подозревать оба движка.

### `ReconcileExistingRows` — сверка существующих строк (R7.2)

Тело перенесено из `GetElementsForRule` (`Spec.cpp`) без изменения **порядка
операций** — порядок здесь контракт, а не деталь реализации:

1. обход `rule.exsist_elements` в исходном порядке;
2. `key_out` собирается из полей **ВЫХОДА** правила (`out_paramrawname`) по ATSIGN;
3. три ветви удаления по порядку: `!hasunic` -> `!out_param.ContainsKey` ->
   `!elements.ContainsKey`; каждая пишет в `guids` значение `false`;
4. сверка значений: сначала несуммарные слоты, затем суммарные, в порядке схемы
   строки, затем непрочитанное поле `destinationParamGuidName`;
5. при `flag_change` -> `elements_mod.Add (key, el)` с присвоенным `exs_guid`;
6. `elements.Delete (key)` и `guids.Add (elemguid, true)` — строка израсходована,
   объект **сопоставлен, НЕ удалён**;
7. второй обход: всё из `exsist_elements`, чего нет в `guids`, удаляется.

| Что перенесено | Как |
|---|---|
| `reader.Read` | 4 вызова, остались в `SpecPlanning.cpp`; в `Spec.cpp` их 0. Всего 8 (4 расчёт + 4 сверка) — критерий эквивалентности |
| `msg_rep` (9 шт.) | свёрнуты в `report (...)` — лямбда с тем же `msg_rep ("Spec", text, NoError, APINULLGuid)`; **тексты не изменены**, они разбираются отчётом |
| имена параметров | `out_param`->`outParam`, `elements_delete`->`elementsDelete`, `elements_mod`->`elementsMod` (стиль модуля); текст сообщения с `out_param` оставлен как есть |
| представление create/update/delete/unchanged | **ещё не введено** — это R7.3/R7.4; план требует менять представление только ПОСЛЕ сравнения |

**Контракт, закреплённый `TestSpecReconcileFixtures` (37 проверок), менять нельзя:**
`out_param` отдаёт первый ключ для выходного значения (дубль старого объекта
удаляется, сопоставленный — нет); при полном совпадении значений строка всё равно
удаляется из `elements` (no-op); `key_out` из выходных, а не уникальных полей;
последняя ветка читает GUID-поле, но результат не использует.

**Идея `report`:** лямбда ловит `rule`, чтобы `msg_rep` не потребовал лишних
параметров в каждой из 9 точек. Это косметика переноса, а не изменение поведения —
поэтому она не трогает числа прогонов.

### `SpecChangePlan` — план изменений (R7.3)

Живёт в `Spec.hpp`, а не в `SpecPlanning.hpp`: тот включает `Spec.hpp`, наоборот
получился бы цикл.

| Поле | Смысл |
|---|---|
| `removals` | `GS::Array<{API_Guid guid, DeleteReason reason}>` — что удалить и почему, **одной структурой** |
| `update` | `ElementDict` — сопоставленные строки с `flag_change` |
| `create` | GUID строк, не сопоставленных ни одному старому объекту |
| `unchanged` | **счётчик**, не копия строки (см. ниже) |
| `deleteOld` | сверка выполнялась? По умолчанию **0** |
| `Matches()` | сверка плана с фактическими списками — страховка от будущей правки |

`DeleteReason`: `NoUniqueFields` (не собрался `key_out`), `NoNewRow`
(`key_out` не найден в `out_param`), `RowAlreadyClaimed` (строка захвачена другим
объектом), `Obsolete` (второй обход, не попал в `guids`).

**Три свойства, которые план держит намеренно:**

- **Наблюдатель, а не второй источник истины.** Заполняется из тех же точек, что
  пишут `elementsMod`/`elementsDelete`, поэтому расхождение невозможно по
  построению. `Matches` — страховка от будущей правки, а не проверка согласованности
  двух источников.
- **Никакого текста на корректную строку.** Требование R7.3 уже выполнялось в коде:
  все 9 вызовов `report` в сверке стоят внутри ветвей отклонения, на совпавшей строке
  не строится ни одного текста. Проверено до внесения изменений — ускорять нечего.
- **`unchanged` — счётчик.** Копия всех свойств ради строки, которую не трогают,
  и есть та лишняя копия, которую запрещает R7.4. Решение R7.4 принято здесь,
  потому что план — его первый потребитель.

**`Obsolete` недостижим при обычном ходе:** объект из `exsist_elements` либо попадает
в `guids`, либо удаляется одной из трёх ранних ветвей. Значение оставлено в
перечислении для исчерпывающей диагностики; отдельной проверки на него нет.

**План опционален:** `GetElementsForRule` и `ReconcileExistingRows` принимают
`SpecChangePlan *plan = nullptr`; рабочий путь его не строит.

### Один владелец payload (R7.4) — прежние поля удалены

`Element` хранит **только** `out_slots`. Четыре прежних поля
(`out_param`, `out_sum_param`, `out_paramrawname`, `out_sum_paramrawname`)
удалены; обращений к ним в `spec/` нет.

| Что | Как |
|---|---|
| `BuildOutputSlots` | строит слоты **напрямую из вклада** (`contribution.outParam`/`outSumParam`), без промежуточного копирования в поля строки |
| `SumContributionIntoRow` | складывает по слотам с `isSum`; «первые MIN(длин)» сохранено дословно, первый суммарный слот = `out_slots.GetSize () - accumulated`. `accumulated` считается ОБРАТНЫМ проходом до первого несуммарного слота (#240): схема строится «сначала выходные, затем суммы», поэтому суммы образуют суффикс, а прямой проход по всем слотам делал стоимость каждого merge зависимой от числа выходных полей |
| `OutSlotsMatchSchema` | считает несуммарные и суммарные слоты по флагу `isSum`; условие прежнее (ни один набор не пуст, числа совпадают) |
| accessor-ы | `OutParamValue`/`OutSumValue`/`OutParamName`/`OutSumName`/`OutParamCount`/`OutSumCount` — **прежняя индексация** (по отдельному массиву на выходные и на суммы), отображение на слоты живёт в одном месте. Новый код читает `OutParam (index)` по объединённой схеме |

**Порядок слотов значим и сохранён:** сначала выходные, затем суммы. Место
источника у слота — флаг `isSum`, но позиция определяет индексы в сверке и при
размещении, поэтому порядок нельзя менять «по вкусу».

**Инвариант суммирования (R7.4):** поведение на неполных массивах то же — лишние
слоты не трогаются, недостающих не создаётся. Длины берутся из схемы строки и
вклада, а не из удалённых массивов, поэтому арифметика не изменилась, но и не
была «улучшена».

**В тестах:** строки сумм, строимые вручную, собираются хелперами `PushSumSlot` /
`PushOutSlot` — без `isSum` строка выглядела бы состоящей только из выходных, и
`SumContributionIntoRow` не нашёл бы накопленных слотов.

### Вызывается из

`Spec::PlanRuleRows` (`Spec.cpp`) — цикл по `rule.elements` и группам.
`Spec::Element` и сверка существующих строк — мимо вклада.

### Проверено тестом

`TestSpecContribution` (`tests/TestSpec.cpp`) — 51 проверка, работает **без
`ElementDict` и без `GetElementsForRule`**. Это и доказывает полезность
разделения: вклад проверяется отдельно от раскладки в агрегат (R6.3).

Покрыто: полный вклад и обе фазы; слот-константа `"1"` (без чтения, значение 1);
выключенный флаг (`Excluded`); непрочитанный уникальный параметр
(исключение + поле помечено + ключ всё равно склеен с `@`); снятие признака
ошибки при `fromMaterial`; неполный выход (`Partial`, пустой `keyOut`);
короткий набор слотов против схемы; два вклада одного ключа строятся независимо.

`TestSpecRowLayout` (`tests/TestSpec.cpp`) — 54 проверки. Покрыто: суммирование
равных массивов; **вклад короче строки** (третий слот не тронут) и **строка
короче вклада** (растёт только перекрытие); `isValid` требуется с обеих сторон
(невалидная сторона и невалидная строка); пустые массивы с обеих сторон; `Created`
с переносом признаков правила и источника; `Merged` с обоими источниками и
сложенной суммой; `SchemaMismatch` — строка не добавлена, но ключ в `outParam`
уже записан; **раскладка в целом даёт тот же словарь строк, что и полный путь**
(число строк, слотов, источников, значения сумм).

### Проверка отсутствия двойного движка и лишних чтений
- `GetElementsForRule`, `PlanRuleRows`, `ReconcileExistingRows`, `PlaceElements`,
  `WriteSpecProperties`, `SpecDG`, `SyncArray` — ровно по одному вызову в пути
  запуска (проверено скриптом по коду с разделением объявлений и вызовов).
  Двойного движка, то есть второго прохода по правилам вне теста, нет. [по коду]
- **План чтения НЕ сериализуется в рабочем пути.** `GetElementsForRule` вызывается
  без аргумента `plan` (`Spec.cpp:767-768`), поэтому `plan == nullptr` и
  `SpecChangePlan` не строится вовсе; наборы тестов передают `plan` явно, чтобы
  проверять решения. Это противоположность «полной сериализации плана» из
  критерия R9.4. [по коду]
- **`ElementsRead` в пути запуска ровно один** (`:753`) при двух наполнениях
  `readContext.read`: `GetParamToReadFromRule` (`:623`) и `AddExistingReadRequests`
  (`:714`). Пакетное чтение выполняется один раз уже после диалога, то есть
  план накапливается, а не исполняется дважды. [по коду]
- Второй вызов `ElementsRead` (`:2788`) относится к проверке правила по GUID
  свойства-правила, а не к запуску Spec: он читает один элемент по
  `CollectRuleDependencies (rule).read`. Принято за лишнее чтение ошибочно —
  это отдельная публичная функция для UI-валидатора. [по коду]
- Источники правил выбираются взаимоисключающими ветками: `GetSelectedElements`
  (`:167`) → если выделение пусто, `GetRuleFromDefaultElem` (`:179`) → если и
  правил нет, `ACAPI_Element_GetElemList` по всем видимым (`:183`). Условия
  прогрессивно ужесточаются, повторной выборки той же модели нет. [по коду]
- `ACAPI_GetOwnResModule` (10 вызовов) — локальное чтение строк ресурсов для
  отчётов и диалогов, а не обход модели; дорогим вызовом не является. `ACAPI_Interface`
  (7) — UI-подсветка и ход процесса, в JSON-пути не выполняется. [по коду]
- Границы доказательства: инвентарь снят **по коду**, а не измереном счётчиком на
  прогоне. Он доказывает отсутствие второго прохода в исходниках, но не измеряет
  число вызовов `ElementsRead` внутри `ParamHelpers` — там циклы по элементам и
  по свойствам, и их количество кодом верхнего уровня не определяется. Проверка
  фактического числа дорогих вызовов остаётся за измеренным gate (R10.6).
