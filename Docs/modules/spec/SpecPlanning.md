## SpecPlanning (вклад источника)

Новый внутренний модуль блока R6. Отвечает за одну сущность: **вклад одного
источника** в итоговую строку спецификации.

| Что | Где |
|---|---|
| `MissingField` | `SpecPlanning.hpp` — непрочитанное поле + признак «ошибка элемента» |
| `ContributionStatus` | `SpecPlanning.hpp` — `Excluded` / `Empty` / `Partial` / `Complete` |
| `RuleContribution` | `SpecPlanning.hpp` — источник, статус, значения по слотам, ключи, пропуски |
| `BuildContribution` | `SpecPlanning.cpp` — **фаза 1**: флаг, уникальные параметры, ключ, суммы |
| `ReadContributionOutputs` | `SpecPlanning.cpp` — **фаза 2**: выходные слоты и ключ выхода |
| `ClassifyContribution` | `SpecPlanning.cpp` — статус от фактических размеров и схемы |

### Разделение двух сущностей

`Spec::Element` — ИТОГОВАЯ строка, накопительный агрегат по ключу; то, что
уходит в сверку и создание. `RuleContribution` — данные ОДНОГО источника за один
проход цикла. До R6.2 оба понятия жили в одном типе.

### Почему две фазы, а не одна

В исходном цикле `elements.ContainsKey (key)` стоит **после** чтения сумм, а
ключ известен только с конца чтения уникальных параметров. Выходные слоты
читаются только в ветке «ключа ещё нет» — то есть только для первого
представителя. Слияние фаз заставило бы читать выход у каждого источника и,
что важнее, заносило бы неполный выход второго источника в отчёт как ошибку,
хотя раньше он молча игнорировался.

### Границы

- Вклад **не накапливает вклады всех элементов модели** в отдельном массиве —
  это прямо запрещено критерием выхода R6 («нет удвоения рабочего набора»).
  Массив вкладов допускается только в regression-режиме R6.5.
- Не меняет ключи строк, порядок первого представителя и арифметику суммирования
  (это R6.3/R6.4).
- Политика отказов (`stop_on_error`, счётчики `not_found_*`, `msg_rep`) осталась
  в `PlanRuleRows`. Вклад сообщает, **что** не прочитано; решение принимает
  вызывающая.

### Раскладка в агрегат (R6.3)

| Что | Где |
|---|---|
| `RowAddition` | `SpecPlanning.hpp` — `Created` / `Merged` / `SchemaMismatch` |
| `SumContributionIntoRow` | `SpecPlanning.cpp` — суммирование в существующую строку |
| `AddContributionToRow` | `SpecPlanning.cpp` — создание или слияние в словаре строк |

**Суммирование неполных массивов — поведение, а не баг.** Сохранено дословно:

- складываются только первые `nsumm = MIN(длин)` слотов; слоты сверх `nsumm` не
  трогаются;
- слот складывается только при `isValid` у обеих сторон, иначе остаётся как есть;
- размеры никогда не выравниваются.

Строгая проверка «длины равны, иначе ошибка» была бы **улучшением, меняющим
результат**, — этого шаг не делает. Наблюдение зафиксировано в `IDEA.md` как
кандидат в **F1** (безопасность неполного расчёта), само F1 не выполнялось и
требует отдельного согласования политики.

**Порядок операций, который обязан сохраняться:**

1. при `Created` запись `outParam[keyOut] = key` делается **до** проверки схемы —
   ключ попадает в словарь даже для отброшенной строки;
2. при `Merged` источник дописывается **до** суммирования;
3. выходные слоты берутся из вклада как есть, без пересчёта и фильтрации.


### Общая выходная схема (R6.4)

`OutputSlot {rawname, value, isSum}` и `Element::out_slots` — имя и значение
слота лежат рядом, поэтому рассинхрон между `out_paramrawname[k]` и
`out_param[k]` невозможен по построению.

| Что | Где |
|---|---|
| `OutputSlot`, `OutputSlots` | `Spec.hpp` — слот и массив слотов |
| `Element::out_slots` | `Spec.hpp` — схема строки |
| `OutParam(i)` / `OutSlotName(i)` / `OutSlotCount()` | `Spec.hpp` — прежнее поведение по индексу |
| `TryGetOutSlot(i, ...)` | `Spec.hpp` — имя+значение слота, `false` вне диапазона |
| `BuildOutputSlots` | `SpecPlanning.cpp` — внутренняя, строит схему один раз на строку |
| обновление значений сумм | `SpecPlanning.cpp`, в том же цикле суммирования |

**Производительность:** схема копируется один раз на строку (как раньше два
массива имён), lookup на ячейку не добавлен — вместо обращения к имени по
индексу прямой проход по слотам. Обновление сумм не добавляет проходов.

**Двойная правда — осознанно и временно:** прежние поля `out_param`,
`out_sum_param`, `out_paramrawname`, `out_sum_paramrawname` оставлены, потому что
accessor-ы читают их. Расхождение возможно только в отладочной сборке и должно
быть поводом для теста, а не для молчаливого поведения.

Проверено `TestSpecRowSlots` — 28 проверок: порядок/имена/значения против
прежних массивов по каждому индексу, безопасный ответ вне диапазона, актуальность
сумм после слияния, неизменность выходного слота первого представителя, отсутствие
схемы у отброшенной строки, стабильность размера при трёх слияниях.

### Вызывается из

`Spec::PlanRuleRows` (`Spec.cpp`) — цикл по `rule.elements` и группам.
`Spec::Element` и сверка существующих строк — мимо вклада.

### Проверено тестом

`TestSpecContribution` (`tests/TestSpec.cpp`) — 51 проверка, работает **без
`ElementDict` и без `GetElementsForRule`**. Это и доказывает полезность
разделения: вклад проверяется отдельно от раскладки в агрегат (R6.3).

Покрыто: полный вклад и обе фазы; слот-константа `"1"` (без чтения, значение 1);
выключенный флаг (`Excluded`); непрочитанный уникальный параметр
(исключение + поле помечено + ключ всё равно склеен с `@`); снятие признака
ошибки при `fromMaterial`; неполный выход (`Partial`, пустой `keyOut`);
короткий набор слотов против схемы; два вклада одного ключа строятся независимо.

`TestSpecRowLayout` (`tests/TestSpec.cpp`) — 54 проверки. Покрыто: суммирование
равных массивов; **вклад короче строки** (третий слот не тронут) и **строка
короче вклада** (растёт только перекрытие); `isValid` требуется с обеих сторон
(невалидная сторона и невалидная строка); пустые массивы с обеих сторон; `Created`
с переносом признаков правила и источника; `Merged` с обоими источниками и
сложенной суммой; `SchemaMismatch` — строка не добавлена, но ключ в `outParam`
уже записан; **раскладка в целом даёт тот же словарь строк, что и полный путь**
(число строк, слотов, источников, значения сумм).
