Перенумерация позиций по правилам из свойств: числовые и текстовые позиции, нулевое заполнение, группировка по критериям и разделителям. [по коду]

## Единое окно результата (#256)

Прежде каждая точка отказа открывала своё всплывающее окно
(`ACAPI_WriteReport (…, true)`), а ошибки по элементам шли строками в отчёт без
привязки к правилу. Теперь сообщения копятся в `RenumRunResult` и показываются
одним окном `RuleSelectDialog` в режиме `isReadOnly` — как в Spec (#245).

**Что показывает окно:**

- строка на каждое правило, участвовавшее в запуске; пять колонок из ресурса:
  `Элементов` / `Изм.` / `Игн.` / `Проп.` / `Ошиб.`. Колонки отбора добавлены
  потому, что без них из «Элементов» не видно, куда делась разница с «Изм.» —
  выглядит так, будто позицию поменяли не у всех;
- имя правила в тексте ошибки **не повторяется**: оно уже стоит в своей строке
  таблицы, а повторённое имя съедало ширину и без того узкого поля сообщения;
- `data.valueColumnWidth` задаёт ширину колонки: подписи обрезаются, если
  колонка уже, чем заголовок. Окно 32590 расширено до 680 px под пять колонок;
- правило с сообщением об ошибке — красное (`data.color`), текст идёт внизу в
  виде «[ИМЯ] — текст»;
- сообщения без правила и итог по запуску (`RenumWrittenTotalId`) — внизу, без
  привязки;
- отвергнутые правила (`rule.state == false`) регистрируются **до** проверки на
  пустой результат: иначе «правило отработало вхолостую» выглядело бы как
  «правила не было».

**Изменения поведения (осознанные):**

- **Отсутствующее свойство больше не останавливает весь запуск.** Прежде
  `error_propertyname` вызывал `return false`, и одно негодное правило обнуляло
  нумерацию по всем остальным. Теперь отсутствие отмечает конкретное правило
  (`RenumMissingProps`), остальные дорабатывают.
- Отсутствующие свойства привязаны к правилу-владельцу, а не собраны в общий
  список имён: свойство отсутствует у конкретного правила.
- `RenumRule::n_error` отделён от `n_skip`: элемент с флагом «пропустить»
  отброшен по решению правила, элемент с невалидным значением — по ошибке.

**Формулировки и разделители (#256, по скриншоту пользователя):**

- заголовки колонок короткие — длинные обрезаются по ширине колонки; в этом
  же ряду лежат подписи колонок Spec (90–92: «Создано»/«Изменено»/«Удалено»),
  потому что окно у запусков одно;
- строки 95 и 98 кончались на `« - »`, и число склеивалось с текстом
  («нумерацию77»). Заменено на двоеточие;
- строка 74 дублировала 95 дословно и в коде не использовалась — переименована;
- 97 («Не удалось записать нумерацию») не называла причину; добавлено
  «Проверьте, не заблокированы ли элементы».

**Дефекты отрисовки, найденные по скриншоту (#256):**

- **Не хватало одного таба.** `totalCount = itemCount - 1 + valueCount` давал
  ровно `NameTab + valueCount`, т.е. последний индекс таба колонки уходил за
  `SetHeaderItemCount`. Данные в ячейке оставались, а заголовок пропадал — у
  «Проп.» и «Ошиб.» он был пуст. Теперь `NameTab + valueCount + 1`.
- **`CenterText` не переносит строки по словам:** в `DGStaticItem.hpp` у
  `StaticText` есть только `Truncation` (NoTruncate/EndTruncate/MiddleTruncate),
  метода переноса нет. `\n` в тексте работает (это символ строки), но длинный
  текст обрезается по высоте поля. Поэтому тексты ошибок переписаны без `\n`,
  одной строкой, а имя правила из сообщения убрано.
- Поле сообщения 45 → 65 px, окно 300 → 330 px, список сжат со 180 до 165:
  три строки текста иначе не помещались.

**Границы:**

- `ReNumReadableName` отбрасывает известную приставку целиком, вместе с
  двоеточием; двоеточие внутри имени сохраняется (у формул оно часть имени).
  Замена по слову `property` оставляла бы «:этаж».
- `RenumRuleDisplayName` берёт текст МЕЖДУ первой парой скобок — часть после
  `;` (флаги нулей) отбрасывается. Это прежнее поведение, на котором построен
  диалог выбора правил; без скобок имя пустое, и сообщение уходит вниз окна без
  привязки.
- Показ окна вызывающего не гасится: `ShowRenumResult` при `nullptr` молчит,
  и тогда отказ обязан пережить вызывающий.

## Формула в критерии и разбивке (#249)

Детектор — двойные кавычки, всё между ними — шаблон (`Renum{"%Помещение%x<%Этаж%>"}`).
Непарные кавычки и пустые `""` трактуются как обычное свойство.

**Ключевые решения:**

- Шаблон вырезается **до** `ToLowerCase` правила (`ReNum_GetElement`), иначе
  литерал шаблона стал бы мелким. Имя свойства между `%…%` приводит уже
  `ReplaceProcToBrace`.
- Шаблон **не оборачивается** в `<…>`: `EvalExpression` вычисляет каждую пару
  `<…>` на месте, внешняя обёртка обрезала бы внутреннюю формулу по первой `>`.
  Так же поступает Sync для кавыченной формулы (`Sync.cpp:1774`).
- Зависимости `%имя%` собираются `ParseParamNameMaterial` — по умолчанию как
  **свойства** (`fromMaterial = true`), как в `BuildReadParamDict` (Spec.cpp).
- Имя параметра уникально в пределах правила: `renum_criteria` / `renum_delimetr`
  различаются, чтобы одинаковые шаблоны не получили один ключ в
  `ParamDictValue`.
- Проверка существования свойства для формульной части **не выполняется**;
  формульная часть не попадает и в `error_propertyname`.
- Вычисление идёт существующим путём: `ParamValue.hasFormula` → `Read` →
  `ReadFormula` → `ReplaceParamInExpression` → `EvalExpression`. `ElementsSeparation`
  не знает про формулы и получает уже вычисленную строку.
- **Частичная подстановка:** `ReplaceParamInExpression` подставляет только
  зависимости с `isValid == true`; остальные заменяются пустой строкой, а сам
  факт подстановки возвращается, когда сработала хотя бы одна. Поэтому формула с
  одной битым свойством даст результат вроде `Кx2-` вместо отказа — это
  существующее поведение движка (Sync/Spec), намеренно не менялось.
- Если формула не вычислилась или результат пуст, элемент пропускается с
  сообщением — так же, как при пустом значении критерия (отдельного кода отказа
  не вводилось).
- Ограничение: нулевое заполнение работает только для числовой позиции
  (`RenumPos::FormatToMax` выходит при `!isNum`) — решение владельца, поведение
  не менялось.

- Расположение: `Sources/AddOn/ReNum.cpp:58`

## Версии (AC29)
- AC29 — первый SDK, который собирает аддон как **C++20** (`<LanguageStandard>stdcpp20</LanguageStandard>` в сгенерированном vcxproj; в AC26–28 — `stdcpp17`). Следствие для сравнений: у неконстантного `bool RenumPos::operator== (const RenumPos&)` компилятор добавляет «перевёрнутый» кандидат `y == x`, и `pa == pb` становится неоднозначным (MSVC C2666 в `TestFunc.cpp`). Оператор сделан `const` — поведение не меняется, в C++17 правка нейтральна. [по vcxproj AC29 + лог сборки]
